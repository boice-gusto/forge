# Research: UI Specification

**Feeds:** `012-ui.md`  
**Status:** Phase 0 research  
**Stack candidates:** Next.js app + Vercel AI Elements (ADOPT-LATER) + Forge SDK

---

## Verdict

Operator UI is a **composition root** (`apps/ui`) that speaks only `@forge/sdk`. First viewport jobs: run status, approval inbox, artifact inspection. AI Elements are optional building blocks for chat/tool display — not a second architecture.

---

## Surfaces (MVP)

| Surface | Purpose | Phase |
|---------|---------|-------|
| Approval inbox | Parameter-bound approve/reject | Phase 3 |
| Run inspector | Timeline, interrupts, checkpoints | Phase 3 |
| Demo console | Acme/Gusto scenario launcher | Phase 2–4 |
| Prompt/artifact viewer | Read-only versioned assets | Phase 4 |

---

## Standards

- No LangGraph / BullMQ / ACPX types in UI bundles (fitness test).  
- Approvals show **AI recommendation + policy reason + exact action parameters**.  
- Streaming via Forge event protocol, not raw provider streams.  
- AI Elements: install via registry into `apps/ui` when chat UX is needed; wrap with Forge design tokens.  
- Accessibility: keyboard approve/reject; no color-only status.  
- Company theming via tokens in company package — core ships neutral theme.

---

## Alternatives

| Approach | Decision |
|----------|----------|
| CLI-only | Insufficient for HITL demos |
| Embed LangSmith UI | Coupling; optional link only |
| Heavy dashboard-first | Avoid — approval + run inspector first |

---

## Acceptance

1. Operator can approve a gated run without CLI.  
2. Switching Acme ↔ Gusto demo does not rebuild UI — config/plugin load only.
