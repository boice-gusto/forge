## 1. Purpose

The Forge operator UI is the **human control surface** for workflow runs. It exists because CLI-only flows are insufficient for human-in-the-loop (HITL) demos and production approvals. The UI is a **composition root** that speaks exclusively to `@forge/sdk` — never to LangGraph, BullMQ, Claude SDK, or ACPX types.

**First viewport jobs:**

1. **Approval inbox** — Parameter-bound approve/reject with policy context.
2. **Run inspector** — Timeline, interrupts, checkpoints, artifacts.
3. **Demo console** — Launch Acme/Gusto scenarios (Phase 2–4).

Chat-style UX is secondary. When needed, Vercel AI Elements are **ADOPT-LATER** building blocks, not a parallel architecture.

### 3.1 Fitness test (CI)

`dependency-cruiser` and eslint boundaries **must fail** if `apps/ui/**` imports:

- `langgraph`, `@langchain/*`
- `bullmq`

- `@forge/runtime` internals (non-public paths)
- Any ACPX types

Allowed: `@forge/sdk`, `@forge/schema` (public types only), design-system tokens, AI Elements (when adopted).

### 4.2 Approval inbox

The inbox is the primary HITL surface. Each item represents a pending `ApprovalRequest` from the runtime.

**Required display fields:**

| Field | Source | Notes |
|-------|--------|-------|
| AI recommendation | Provider output (sanitized) | Labelled **“Recommendation — not authorization”** |
| Policy reason | `forge.policy.decide` obligation | Why approval is required |
| Exact action | Tool name + bound parameters | Human sees what will execute |
| Risk class | Policy context | e.g. `external.publish`, `finance.payment` |
| Run context | `runId`, `workflowId`, domain | Link to run inspector |
| Expiry | Gate TTL | Countdown; expired items not actionable |

**Actions:**

- **Approve** — POST `ApprovalDecision { kind: 'approve' }` with CSRF token.
- **Reject** — Requires reason string.
- **Edit then approve** (Phase 4+) — Patch validated by Zod schema per approval type.

**Keyboard accessibility:**

- `j` / `k` navigate queue.
- `a` approve focused item (with confirmation modal for high-risk).
- `r` reject.
- Focus trap in modals; no color-only status (icon + text).

### 4.3 Run inspector

**Sections:**

1. **Header** — Run status, company, workflow, provider, duration, trace link (OTEL/LangSmith optional).
2. **Timeline** — Ordered `ForgeEvent` stream: node start/end, policy decisions, approvals, provider calls (metadata only), sandbox lifecycle.
3. **Interrupts** — Pending and resolved gates with decision audit.
4. **Checkpoints** — Resume points (opaque IDs; no LangGraph checkpoint payloads in UI).
5. **Artifacts** — Outputs, reports, draft content (read-only; sanitized HTML).

**Streaming:** Subscribe to `GET /v1/runs/:runId/events` with
`Accept: text/event-stream`. Events are Forge-owned DTOs, not raw AI SDK
streams.

Decided 2026-08-06: **SSE, content-negotiated on the existing route**, rather
than a separate `/stream` path or a WebSocket. The snapshot and the tail are one
collection in two representations, so the authentication, the 404 and the event
classification are the same lines rather than a second copy — and the copy
nobody sweeps is where an exemption hides. WebSocket was rejected as full duplex
nothing needs, a new dependency, and no graceful degradation to a plain GET.

The tail polls the **durable** store, not an in-process bus: the control plane
usually does not walk the run — a worker does — so a bus would tail perfectly in
the local stack and emit nothing in production. `id:` carries the store's
sequence and `Last-Event-ID` resumes after it, so a client loads the snapshot
and tails without replaying its own history.

Two properties worth keeping: the tail **re-authenticates on every pass**, so a
revoked session stops receiving rather than holding a socket open on a stale
credential; and a span's closing attributes refine a row already delivered, so
the snapshot remains authoritative for final state.

### 4.4 Demo console

Supports [016-demo-scenarios](./016-demo-scenarios.md) acceptance:

```text
/demo
  ├── Company selector (acme | gusto)
  ├── Scenario list (A1–A5, G1–G5)
  ├── Fixture selector (optional)
  └── Run → deep-link to /runs/:id
```

Switching Acme ↔ Gusto **must not rebuild the UI** — only company config/plugin load changes. Architecture test: no company-specific routes hardcoded in core UI; scenario list loaded from manifest or static catalog keyed by company id.

### 4.5 Prompt/artifact viewer (Phase 4)

Read-only view of versioned prompt assets and run outputs:

- Prompt id + semver + content hash.
- No inline editing of prompts in UI (prompts are versioned assets in repo).
- Diff between prompt versions for audit.

## 5. Data contracts (SDK DTOs)

UI consumes only stable SDK types. Example shapes (finalize in `@forge/schema`):

```ts
interface ApprovalInboxItem {
  approvalId: string
  runId: string
  workflowId: string
  createdAt: string
  expiresAt: string
  recommendation: string        // sanitized
  policyReason: string
  action: { tool: string; argsPreview: Record<string, unknown> }
  riskClass: string
  status: 'pending' | 'approved' | 'rejected' | 'expired'
}

interface RunTimelineEvent {
  seq: number
  at: string
  kind: 'node' | 'policy' | 'approval' | 'provider' | 'sandbox' | 'log'
  label: string
  detail?: Record<string, unknown>
  traceId?: string
}
```

DTOs must not expose engine checkpoint blobs, Rego source, or raw provider message arrays.

## 6. AI Elements (ADOPT-LATER)

When chat or tool-call visualization is needed:

1. Install components via Vercel AI Elements shadcn registry into `apps/ui/components/ai/`.
2. Wrap with Forge design tokens (spacing, color, typography).
3. Feed components **Forge-normalized** message DTOs, not AI SDK internal types.
4. Never use AI Elements as the approval authority — approvals always go through `ApprovalPort` API.

**Defer until:** Phase 4+ when a scenario requires conversational UX beyond inbox + timeline.

## 8. Security (UI-specific)

Cross-reference [014-security](./014-security.md):

| Control | Requirement |
|---------|-------------|
| CSP | Strict; `default-src 'self'`; no `unsafe-inline` without nonces |
| Model HTML | Sanitize markdown/HTML; never `dangerouslySetInnerHTML` with model output |
| Secrets | Never display full secrets in approval preview; mask tokens |
| CSRF | SameSite cookies + CSRF token on approve/reject |
| Headers | HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, COOP/CORP |
| Auth | Approver identity from IdP; role checked server-side by policy |

Integration tests assert security headers on UI responses (Phase 4 gate).

## 11. Acceptance criteria

1. Operator can **approve a gated run without CLI** (Playwright: A1, A4, G1).
2. Switching Acme ↔ Gusto demo does **not rebuild UI** — config/plugin load only.
3. Approval card shows **AI recommendation + policy reason + exact action parameters**.
4. `apps/ui` bundle passes architecture fitness (no forbidden imports).
5. Keyboard approve/reject works; status not color-only.
